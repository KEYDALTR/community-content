## Introduction

Podman runs containers without a central daemon, and it can run them entirely as an unprivileged user. That second part is the interesting one for a server: a process that breaks out of a rootless container lands as an ordinary user with no privileges, not as root on the host.

In this tutorial you install Podman, run a container as a normal user, and see for yourself how the user IDs are mapped on the host. You then turn that container into a systemd service using Quadlet, and make it survive both logout and a reboot.

Quadlet is the supported way to run Podman containers under systemd. You describe the container in a small unit-like file, and systemd generates the service for you. It replaced `podman generate systemd`, which is deprecated.

Podman is free and open source (Apache-2.0). The steps were tested on Ubuntu 24.04 LTS with Podman 4.9.3.

**Prerequisites**

* One server with a fresh Ubuntu 24.04 install
* Root access for the installation steps
* SSH access, because rootless Podman needs a real login session (explained in Step 3)

This tutorial uses the following example values:

* Username: `holu`
* IPv4 address: `10.0.0.1`
* Domain: `example.com`

Replace them with your own values.

## Step 1 - Install Podman

As root, install the package:

```bash
apt update
apt install -y podman
```

Check the version:

```bash
podman --version
```

```
podman version 4.9.3
```

The Ubuntu package pulls in the pieces rootless mode needs, so there is nothing else to install:

```bash
dpkg -l | grep -E "^ii  (crun|slirp4netns|passt|uidmap|fuse-overlayfs) " | awk '{print $2,$3}'
```

```
crun 1.14.1-1
fuse-overlayfs 1.13-1
passt 0.0~git20240220.1e6f92b-1
slirp4netns 1.2.1-1build2
uidmap 1:4.13+dfsg1-4ubuntu3.2
```

`uidmap` provides `newuidmap` and `newgidmap`, the setuid helpers that let an unprivileged user claim a range of subordinate user IDs. Without it, rootless mode does not work at all.

## Step 2 - Create a user for your containers

Containers should not run under your admin account. Create a separate user:

```bash
adduser --disabled-password --gecos "" holu
```

Ubuntu assigns a range of subordinate user and group IDs automatically:

```bash
grep holu /etc/subuid /etc/subgid
```

```
/etc/subuid:holu:100000:65536
/etc/subgid:holu:100000:65536
```

That means user IDs inside the container get mapped into the range starting at 100000 on the host, 65536 of them. If these lines are missing on your system, add them with `usermod --add-subuids 100000-165535 --add-subgids 100000-165535 holu`.

## Step 3 - Run your first rootless container

Log in as `holu` over SSH, not with `su`. This matters more than it looks. When you switch with `su - holu`, systemd does not create a user session, so `XDG_RUNTIME_DIR` stays empty and Podman falls back to a degraded mode:

```
time="..." level=warning msg="The cgroupv2 manager is set to systemd but there is no systemd user session available"
time="..." level=warning msg="For using systemd, you may need to log in using a user session"
time="..." level=warning msg="Alternatively, you can enable lingering with: `loginctl enable-linger 1000` (possibly as root)"
time="..." level=warning msg="Falling back to --cgroup-manager=cgroupfs"
time="..." level=warning msg="Failed to add pause process to systemd sandbox cgroup: dbus: couldn't determine address of session bus"
```

Log in over SSH instead:

```bash
ssh holu@10.0.0.1
```

Then confirm the environment is sane:

```bash
echo $XDG_RUNTIME_DIR
podman info --format "rootless={{.Host.Security.Rootless}} cgroup={{.Host.CgroupManager}}"
```

```
/run/user/1000
rootless=true cgroup=systemd
```

Now pull and run something. Note the full image name:

```bash
podman run -d --name web -p 8080:80 docker.io/library/nginx:alpine
```

If you shorten that to `nginx`, Podman refuses:

```
Error: short-name "nginx" did not resolve to an alias and no unqualified-search registries are defined in "/etc/containers/registries.conf"
```

Ubuntu ships `/etc/containers/registries.conf` with no search registries configured, which is a deliberate choice: a short name is ambiguous and could resolve to a different registry than you expect. Write the full name and you always know which image you got.

Another limit you will hit immediately is privileged ports. An unprivileged user cannot bind below 1024:

```
Error: rootlessport cannot expose privileged port 80, you can add 'net.ipv4.ip_unprivileged_port_start=80' to /etc/sysctl.conf (currently 1024), or choose a larger port number (>= 1024): listen tcp 0.0.0.0:80: bind: permission denied
```

Step 7 covers that. For now, check the container on port 8080:

```bash
podman ps --format "{{.Names}} {{.Status}} {{.Ports}}"
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8080/
```

```
web Up 3 seconds 0.0.0.0:8080->80/tcp
200
```

## Step 4 - Check what rootless actually changes

This is worth doing once, because it makes the security argument concrete instead of abstract.

Inside the container, nginx runs as root:

```bash
podman exec web id
```

```
uid=0(root) gid=0(root)
```

On the host, look at the same processes:

```bash
ps aux | grep "[n]ginx"
```

```
holu        8189  nginx: master process nginx -g daemon off;
100100      8215  nginx: worker process
100100      8216  nginx: worker process
```

The master process belongs to `holu`, and the workers show up as UID `100100`. nginx runs its workers as UID 100 inside the container, and 100000 + 100 is 100100, straight out of the `/etc/subuid` range from Step 2. Those IDs belong to no real account on the host, so a process escaping the container has fewer rights than a normal user.

Remove the test container before continuing:

```bash
podman rm -f web
```

## Step 5 - Turn the container into a service with Quadlet

Running containers by hand is fine for testing, but a server needs them started and restarted automatically. Quadlet files go into a directory systemd scans for the user:

```bash
mkdir -p ~/.config/containers/systemd
```

Create `~/.config/containers/systemd/web.container`:

```ini
[Unit]
Description=nginx test container

[Container]
Image=docker.io/library/nginx:alpine
PublishPort=8080:80

[Install]
WantedBy=default.target
```

The file is not a service unit. A systemd generator reads it and writes the real unit at boot and on reload, which is why the service is called `web.service` after the file name:

```bash
systemctl --user daemon-reload
systemctl --user start web.service
systemctl --user is-active web.service
```

```
active
```

Do not run `systemctl --user enable web.service`. Generated units cannot be enabled, and you get:

```
Failed to enable unit: Unit /run/user/1000/systemd/generator/web.service is transient or generated.
```

The `[Install]` section inside the `.container` file already does that job. This catches people who are used to writing service files by hand.

Logs work as usual:

```bash
journalctl --user -u web.service -n 4 --no-pager
```

```
systemd-web[1122]: 2026/08/12 18:25:08 [notice] 1#1: start worker process 29
```

## Step 6 - Keep the service running after logout

By default, a user's systemd instance stops when their last session ends, taking the containers with it. Log out and check from a root shell:

```bash
systemctl is-active user@1000.service
ss -tlnp | grep ":8080 "
```

```
inactive
```

Nothing is listening on 8080 anymore. Enable lingering, as root, so the user manager starts at boot and keeps running with nobody logged in:

```bash
loginctl enable-linger holu
```

```bash
loginctl show-user holu | grep -i linger
```

```
Linger=yes
```

Now reboot the server and check again once it is back, without logging in as `holu`:

```bash
systemctl is-active user@1000.service
ss -tlnp | grep ":8080 "
ps aux | grep "[n]ginx: master"
```

```
active
LISTEN 0  4096  *:8080  *:*  users:(("rootlessport",pid=1107,fd=12))
holu  1124  nginx: master process nginx -g daemon off;
```

The container came back on its own. Lingering is the piece people forget, and the symptom is confusing: everything works while you are logged in and the service is gone the next morning.

## Step 7 - Publish a privileged port

If the service has to answer on port 80 or 443 directly, lower the threshold for unprivileged ports. As root, create `/etc/sysctl.d/99-rootless-ports.conf`:

```
net.ipv4.ip_unprivileged_port_start=80
```

Apply it:

```bash
sysctl -p /etc/sysctl.d/99-rootless-ports.conf
```

```
net.ipv4.ip_unprivileged_port_start = 80
```

The container can now bind port 80 as `holu`:

```bash
podman run -d --rm --name p80 -p 80:80 docker.io/library/nginx:alpine
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1/
```

```
200
```

This lowers the limit for every unprivileged process on the host, not just Podman, so set it to the lowest port you actually need rather than to 1. Putting a reverse proxy in front and leaving the containers on high ports keeps the default in place and gives you TLS and routing in one spot.

## Conclusion

You now run containers as an unprivileged user, with host UIDs mapped into a subordinate range, managed by systemd through Quadlet and surviving reboots.

To add more services, drop another `.container` file next to the first one and reload. Quadlet also understands `.volume`, `.network` and `.pod` files, so a small stack can be described without Compose. The options available in each section are listed in the [podman-systemd.unit manual](https://docs.podman.io/en/latest/markdown/podman-systemd.unit.5.html).
