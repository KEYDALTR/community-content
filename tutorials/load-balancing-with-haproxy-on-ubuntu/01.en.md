## Introduction

HAProxy is a TCP and HTTP load balancer that has been around since 2000 and still runs in front of a lot of large sites. Compared to using a general-purpose web server for the same job, it gives you finer control over health checks, queuing and per-server state, and it tells you exactly why it took a backend out of rotation.

In this tutorial you put HAProxy in front of two web servers. You add health checks so a broken backend is removed automatically, terminate TLS at the load balancer, forward the real client IP to the backends, and enable a statistics page that is not reachable from the internet.

To keep the tutorial to a single server, both backends run on the same machine on different ports. In a real setup they would be separate servers, and you would point HAProxy at their private network addresses instead of `127.0.0.1`. Everything else stays the same.

HAProxy is free and open source (GPL-2.0). The steps were tested on Ubuntu 24.04 LTS with HAProxy 2.8.16 and nginx 1.24.0.

**Prerequisites**

* One server with a fresh Ubuntu 24.04 install
* Root access, or a user with `sudo`
* Ports 80 and 443 reachable from the internet if you want to test from outside

This tutorial uses the following example values:

* Username: `holu`
* IPv4 address: `10.0.0.1`
* Domain: `example.com`

Replace them with your own values.

## Step 1 - Install HAProxy

Update the package lists and install HAProxy from the Ubuntu repository:

```bash
sudo apt update
sudo apt install -y haproxy
```

Check which version you got:

```bash
haproxy -v
```

On Ubuntu 24.04 this is the 2.8 long-term supported branch:

```
HAProxy version 2.8.16-0ubuntu0.24.04.3 2026/06/19 - https://haproxy.org/
Status: long-term supported branch - will stop receiving fixes around Q2 2028.
```

The package enables and starts the service right away. That is harmless at this point, because the default configuration file that ships with Ubuntu contains only the `global` and `defaults` sections and no frontend, so HAProxy is not listening on any port yet.

## Step 2 - Set up two backend web servers

Install nginx to act as the two backends:

```bash
sudo apt install -y nginx
```

nginx binds to port 80 during installation. HAProxy needs that port, so remove the default site:

```bash
sudo rm /etc/nginx/sites-enabled/default
```

Create a document root for each backend with content you can tell apart:

```bash
sudo mkdir -p /var/www/web1 /var/www/web2
echo "Backend 1" | sudo tee /var/www/web1/index.html
echo "Backend 2" | sudo tee /var/www/web2/index.html
```

Create the file `/etc/nginx/sites-available/backends`:

```nginx
server {
    listen 127.0.0.1:8081;
    root /var/www/web1;
    location /health { return 200 "ok\n"; }
}

server {
    listen 127.0.0.1:8082;
    root /var/www/web2;
    location /health { return 200 "ok\n"; }
}
```

Both servers listen on `127.0.0.1` only, so nobody can reach them directly from outside and bypass the load balancer. The `/health` location is what HAProxy will poll in the next step. A separate health endpoint is better than checking `/`, because it lets an application report that it is unhealthy while its home page still renders.

Enable the site and reload nginx:

```bash
sudo ln -s /etc/nginx/sites-available/backends /etc/nginx/sites-enabled/backends
sudo nginx -t
sudo systemctl reload nginx
```

Confirm both backends answer:

```bash
curl http://127.0.0.1:8081/
curl http://127.0.0.1:8082/
```

```
Backend 1
Backend 2
```

## Step 3 - Configure load balancing with health checks

Back up the shipped configuration before you change it:

```bash
sudo cp /etc/haproxy/haproxy.cfg /etc/haproxy/haproxy.cfg.orig
```

Append the following to `/etc/haproxy/haproxy.cfg`. Leave the existing `global` and `defaults` sections alone, they already set `mode http` and sane timeouts:

```haproxy
frontend web_frontend
    bind :80
    default_backend web_servers

backend web_servers
    balance roundrobin
    option httpchk GET /health
    server web1 127.0.0.1:8081 check inter 2s fall 3 rise 2
    server web2 127.0.0.1:8082 check inter 2s fall 3 rise 2
```

What the server options do:

* `check` turns on health checking for that server
* `inter 2s` runs a check every two seconds
* `fall 3` takes the server out after three consecutive failures
* `rise 2` puts it back after two consecutive successes

The defaults are `inter 2s fall 3 rise 2`, so you can leave them out. They are spelled out here because these are the numbers you will want to tune first: raising `fall` makes HAProxy more tolerant of a flapping backend, lowering `inter` detects an outage faster at the cost of more check traffic.

Validate the file before restarting. HAProxy checks configuration syntax without touching the running service:

```bash
sudo haproxy -c -f /etc/haproxy/haproxy.cfg
```

```
Configuration file is valid
```

Restart HAProxy:

```bash
sudo systemctl restart haproxy
```

Send a few requests and watch them alternate:

```bash
for i in $(seq 1 6); do curl -s http://127.0.0.1/; done
```

```
Backend 1
Backend 2
Backend 1
Backend 2
Backend 1
Backend 2
```

If HAProxy refuses to start here, check whether something else still holds port 80:

```
[ALERT] : Binding [/etc/haproxy/haproxy.cfg:37] for frontend web_frontend: cannot bind socket (Address already in use) for [0.0.0.0:80]
[ALERT] : [/usr/sbin/haproxy.main()] Some protocols failed to start their listeners! Exiting.
```

That message means the default nginx site is still enabled, or nginx was not reloaded after you removed it. `sudo ss -tlnp | grep ':80 '` shows the process holding the port. One thing worth knowing: after `systemctl reload nginx`, the old worker processes keep the listening socket for a moment while they finish serving open connections, so a restart that happens immediately afterwards can still fail. `sudo systemctl restart nginx` closes it right away.

## Step 4 - Test failover

Make one backend report itself as unhealthy. In `/etc/nginx/sites-available/backends`, change the `/health` line in the `127.0.0.1:8081` server block so it returns 503:

```nginx
    location /health { return 503; }
```

Reload nginx and wait for the health check to fail three times:

```bash
sudo systemctl reload nginx
sleep 9
```

Confirm the endpoint really returns 503 before you look at HAProxy, otherwise you end up debugging the wrong side:

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8081/health
```

```
503
```

HAProxy logs the reason it dropped the server. Limit the output to the last few minutes, since the journal still holds entries from earlier restarts and an old line here is easy to mistake for a current one:

```bash
sudo journalctl -u haproxy --since "5 minutes ago" | grep "is DOWN"
```

```
Server web_servers/web1 is DOWN, reason: Layer7 wrong status, code: 503, info: "Service Temporarily Unavailable", check duration: 0ms. 1 active and 0 backup servers left. 0 sessions active, 0 requeued, 0 remaining in queue.
```

`Layer7` means the check reached the application and got an answer HAProxy did not accept. A backend that is completely down would report `Layer4 connection problem` instead. That distinction is useful when you debug: Layer4 points at the network or a stopped service, Layer7 points at the application itself.

All requests now go to the remaining server:

```bash
for i in $(seq 1 6); do curl -s http://127.0.0.1/; done
```

```
Backend 2
Backend 2
Backend 2
Backend 2
Backend 2
Backend 2
```

Change the line back to `return 200 "ok\n";` and reload nginx. After two successful checks the server comes back on its own:

```
Server web_servers/web1 is UP, reason: Layer7 check passed, code: 200, check duration: 0ms. 2 active and 0 backup servers online. 0 sessions requeued, 0 total in queue.
```

## Step 5 - Add TLS termination

HAProxy expects the certificate and the private key in one PEM file. This trips up people coming from nginx, which takes them as two separate directives. If you point `crt` at a certificate alone, it looks for the key next to it and fails at startup:

```
[ALERT] : config : parsing [...] : 'bind :8443' in section 'frontend' : No Private Key found in '/etc/haproxy/certs/site.crt.key'.
```

Create a directory for the certificate:

```bash
sudo mkdir -p /etc/haproxy/certs
sudo chmod 700 /etc/haproxy/certs
```

For a domain you control, get a certificate from Let's Encrypt (see [Add SSL Certificate with Lets Encrypt](https://community.hetzner.com/tutorials/add-ssl-certificate-with-lets-encrypt-to-nginx-on-ubuntu-20-04)) and concatenate `fullchain.pem` and `privkey.pem` into one file. To test the setup without a domain, generate a self-signed certificate:

```bash
sudo openssl req -x509 -newkey rsa:2048 -nodes -days 365 \
  -keyout /etc/haproxy/certs/site.key \
  -out /etc/haproxy/certs/site.crt \
  -subj "/CN=example.com"
```

Combine both parts into the file HAProxy reads, and keep it readable by root only:

```bash
sudo sh -c 'cat /etc/haproxy/certs/site.crt /etc/haproxy/certs/site.key > /etc/haproxy/certs/site.pem'
sudo chmod 600 /etc/haproxy/certs/site.pem
```

Replace the `frontend web_frontend` section in `/etc/haproxy/haproxy.cfg` with:

```haproxy
frontend web_frontend
    bind :80
    bind :443 ssl crt /etc/haproxy/certs/site.pem
    http-request redirect scheme https unless { ssl_fc }
    http-request set-header X-Forwarded-Proto https if { ssl_fc }
    default_backend web_servers
```

`ssl_fc` is true when the request arrived over TLS. The first rule redirects plain HTTP to HTTPS, the second tells the backend which scheme the client actually used, which applications need when they build absolute URLs.

Check and reload:

```bash
sudo haproxy -c -f /etc/haproxy/haproxy.cfg
sudo systemctl reload haproxy
```

Plain HTTP now returns a redirect:

```bash
curl -sI http://127.0.0.1/ | head -3
```

```
HTTP/1.1 302 Found
content-length: 0
location: https://127.0.0.1/
```

And the HTTPS request is served. `-k` tells curl to accept the self-signed certificate; drop it once you use a real one:

```bash
curl -k https://127.0.0.1/
```

```
Backend 1
```

## Step 6 - Pass the real client IP to the backends

Right now every request reaches the backends from `127.0.0.1`, so their access logs are useless and any IP-based logic in the application sees the load balancer instead of the visitor.

Add `option forwardfor` to the backend section in `/etc/haproxy/haproxy.cfg`:

```haproxy
backend web_servers
    option forwardfor
    balance roundrobin
    option httpchk GET /health
    server web1 127.0.0.1:8081 check inter 2s fall 3 rise 2
    server web2 127.0.0.1:8082 check inter 2s fall 3 rise 2
```

That adds an `X-Forwarded-For` header, but nginx still logs the connection address until you tell it to trust the header. Add these two lines to **both** server blocks in `/etc/nginx/sites-available/backends`:

```nginx
    set_real_ip_from 127.0.0.1;
    real_ip_header X-Forwarded-For;
```

Doing this in only one block is easy to miss, and the result is confusing: one backend logs real addresses while the other keeps logging `127.0.0.1`, depending on which one served the request.

`set_real_ip_from` must list the address HAProxy connects from. On separate servers that is the load balancer's private IP, not `127.0.0.1`. Only list addresses you control, since anything in that list is allowed to claim an arbitrary client IP.

Reload both services:

```bash
sudo nginx -t
sudo systemctl reload nginx
sudo haproxy -c -f /etc/haproxy/haproxy.cfg
sudo systemctl reload haproxy
```

Request the site from another machine, then look at the backend log:

```bash
sudo tail -2 /var/log/nginx/access.log
```

```
<your-ip> - - [12/Aug/2026:18:08:47 +0000] "GET / HTTP/1.1" 200 10 "-" "curl/8.17.0"
```

## Step 7 - Enable the statistics page

HAProxy ships a status page that shows every server, its state, and the traffic it handled. Append this to `/etc/haproxy/haproxy.cfg`:

```haproxy
listen stats
    bind 127.0.0.1:8404
    stats enable
    stats uri /
    stats refresh 10s
    stats auth holu:<your-password>
```

Two deliberate choices here. The page binds to `127.0.0.1`, so it is not exposed to the internet at all, and `stats auth` adds a password on top of that. The page reveals your backend addresses and traffic patterns, so it does not belong on a public port even with a password.

Reload and confirm the password is enforced:

```bash
sudo haproxy -c -f /etc/haproxy/haproxy.cfg
sudo systemctl reload haproxy
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8404/
```

```
401
```

To view the page, forward the port over SSH from your local machine:

```bash
ssh -L 8404:127.0.0.1:8404 holu@10.0.0.1
```

While that session is open, open `http://127.0.0.1:8404/` in your browser and log in with the credentials from `stats auth`.

The same data is available as CSV, which is handy for scripting or a quick check over SSH:

```bash
curl -s -u holu:<your-password> "http://127.0.0.1:8404/;csv" | cut -d, -f1,2,18
```

```
# pxname,svname,status
web_frontend,FRONTEND,OPEN
web_servers,web1,UP
web_servers,web2,UP
web_servers,BACKEND,UP
```

## Conclusion

You now have HAProxy distributing requests across two backends, removing a server from rotation when its health check fails and adding it back when it recovers, terminating TLS, forwarding the real client IP, and reporting its state on a page that is only reachable through an SSH tunnel.

To move the backends onto their own servers, put them in a private network, change the `server` lines to the private addresses, and update `set_real_ip_from` to the load balancer's private IP. Keep the backends listening on private addresses only, so requests cannot skip the load balancer.

From here, `balance leastconn` suits long-lived connections better than round robin, and `cookie` based session stickiness helps with applications that keep state in local memory. Both are documented in the [HAProxy configuration manual](https://docs.haproxy.org/2.8/configuration.html).
