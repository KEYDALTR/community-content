## Introduction

A nightly dump gets you back to last night. It does not help when someone drops a table at 14:30 and you notice at 15:00. Point-in-time recovery (PITR) fills that gap: pgBackRest takes a base backup, PostgreSQL keeps writing its write-ahead log (WAL) into the same repository, and a restore can stop at any moment covered by those logs.

In this tutorial you install PostgreSQL and pgBackRest, turn on WAL archiving, take a backup, then destroy a table on purpose and bring the database back to the second before it happened. The restore is verified by reading the rows back out, not just by a "completed successfully" message.

One warning up front, because it cost the first attempt in this tutorial: the recovery target is compared against transaction commit times with sub-second precision. Getting that wrong gives you a restore that appears to work and silently misses your data. Step 5 shows exactly what that looks like.

pgBackRest is free and open source (MIT). The steps were tested on Ubuntu 24.04 LTS with PostgreSQL 16.14 and pgBackRest 2.50.

**Prerequisites**

* One server with a fresh Ubuntu 24.04 install
* Root access, or a user with `sudo`
* Enough free disk space for a second copy of the database

This tutorial uses the following example values:

* Username: `holu`
* IPv4 address: `10.0.0.1`
* Domain: `example.com`
* Database: `shop`

Replace them with your own values.

## Step 1 - Install PostgreSQL and pgBackRest

Both are in the Ubuntu repository:

```bash
sudo apt update
sudo apt install -y postgresql pgbackrest
```

Check what you got and confirm the cluster is running:

```bash
psql --version
pgbackrest version
pg_lsclusters
```

```
psql (PostgreSQL) 16.14 (Ubuntu 16.14-0ubuntu0.24.04.1)
pgBackRest 2.50
Ver Cluster Port Status Owner    Data directory              Log file
16  main    5432 online postgres /var/lib/postgresql/16/main /var/log/postgresql/postgresql-16-main.log
```

Note the version and the data directory. Both go into the configuration in the next step, and the path contains the major version number, so it will differ on other releases.

## Step 2 - Configure the backup repository

The Ubuntu package already installs `/etc/pgbackrest.conf` with an example that points at a PostgreSQL 13 path. Replace its contents rather than adding a second file:

```
[global]
repo1-path=/var/lib/pgbackrest
repo1-retention-full=2
start-fast=y

[main]
pg1-path=/var/lib/postgresql/16/main
```

`main` is the stanza name, which is just a label for one cluster. It is used in every command from here on. `repo1-retention-full=2` keeps two full backups and expires older ones together with the WAL they need. Without a retention setting the repository grows forever. `start-fast=y` makes PostgreSQL run a checkpoint immediately instead of waiting for the next scheduled one, so backups start without a delay.

The package created `/var/lib/pgbackrest` and `/var/log/pgbackrest` owned by `postgres`. Make sure the configuration is readable by that user:

```bash
sudo chown postgres:postgres /etc/pgbackrest.conf
sudo chmod 640 /etc/pgbackrest.conf
```

This tutorial keeps the repository on the same server, which is the one thing you should change in production. A backup on the disk you are protecting is gone when that disk is. pgBackRest can write to a second host over SSH, or to S3-compatible object storage, by adding the matching `repo1-*` options.

## Step 3 - Enable WAL archiving

A base backup alone only restores to the moment it was taken. Continuous recovery needs every WAL segment since then, handed to pgBackRest as PostgreSQL finishes it:

```bash
sudo -u postgres psql -c "ALTER SYSTEM SET archive_mode = on;"
sudo -u postgres psql -c "ALTER SYSTEM SET archive_command = 'pgbackrest --stanza=main archive-push %p';"
```

`archive_mode` only takes effect after a full restart. A reload is not enough, and skipping this is a common way to end up with a repository that never receives WAL:

```bash
sudo systemctl restart postgresql@16-main
```

Confirm both settings took:

```bash
sudo -u postgres psql -c "SHOW archive_mode;" -c "SHOW archive_command;"
```

```
 archive_mode
--------------
 on

             archive_command
------------------------------------------
 pgbackrest --stanza=main archive-push %p
```

The default `wal_level` of `replica` already logs enough for PITR, so it does not need changing.

## Step 4 - Create the stanza and take the first backup

Initialize the repository for this cluster and verify that archiving actually works end to end:

```bash
sudo -u postgres pgbackrest --stanza=main stanza-create
sudo -u postgres pgbackrest --stanza=main check
```

Both print nothing when they succeed, because the default console log level only reports warnings and errors. Add `--log-level-console=info` when you want to see what happened:

```bash
sudo -u postgres pgbackrest --stanza=main check --log-level-console=info
```

```
INFO: WAL segment 000000030000000000000004 successfully archived to '/var/lib/pgbackrest/archive/main/16-1/0000000300000000/000000030000000000000004-588098b69f0fbdb8ba95dcdeafb65f003489441a.gz' on repo1
INFO: check command end: completed successfully (1112ms)
```

`check` writes a throwaway WAL segment and confirms it reaches the repository. Run it after every configuration change, since a broken `archive_command` otherwise stays invisible until the day you need a restore.

Take a full backup:

```bash
sudo -u postgres pgbackrest --stanza=main --type=full backup
```

Then look at what is in the repository:

```bash
sudo -u postgres pgbackrest --stanza=main info
```

```
stanza: main
    status: ok
    cipher: none

    db (current)
        wal archive min/max (16): 000000010000000000000001/000000010000000000000003

        full backup: 20260812-183256F
            timestamp start/stop: 2026-08-12 18:32:56+00 / 2026-08-12 18:33:00+00
            wal start/stop: 000000010000000000000002 / 000000010000000000000003
            database size: 22MB, database backup size: 22MB
            repo1: backup set size: 2.9MB, backup size: 2.9MB
```

`status: ok` and a WAL range that keeps growing are what you check on a healthy system.

## Step 5 - Restore to a point in time

### Step 5.1 - Create data and destroy it

Create a database with something recognisable in it:

```bash
sudo -u postgres psql -c "CREATE DATABASE shop;"
sudo -u postgres psql -d shop -c "CREATE TABLE orders (id serial PRIMARY KEY, item text, created timestamptz DEFAULT now());"
sudo -u postgres psql -d shop -c "INSERT INTO orders (item) VALUES ('keyboard'),('monitor'),('cable');"
```

Write down the current time. This is the moment you will return to:

```bash
sudo -u postgres psql -At -c "SELECT now();"
```

```
2026-08-12 18:33:24.13822+00
```

Keep every digit. The fractional part matters, as the next step shows.

Now cause the damage:

```bash
sudo -u postgres psql -d shop -c "DROP TABLE orders;"
```

Force the current WAL segment into the repository so the recent history is archived:

```bash
sudo -u postgres psql -c "SELECT pg_switch_wal();"
```

### Step 5.2 - Restore

The cluster must be stopped, because the restore rewrites its data directory:

```bash
sudo systemctl stop postgresql@16-main
```

Restore with a recovery target. `--delta` compares the existing files against the backup and only replaces what differs, which is much faster than emptying the directory first:

```bash
sudo -u postgres pgbackrest --stanza=main --delta \
  --type=time --target="2026-08-12 18:33:24" \
  --target-action=promote restore
```

pgBackRest writes the recovery settings itself. You can see them at the end of `postgresql.auto.conf`:

```
# Recovery settings generated by pgBackRest restore on 2026-08-12 18:33:45
restore_command = 'pgbackrest --stanza=main archive-get %f "%p"'
recovery_target_time = '2026-08-12 18:33:24'
recovery_target_action = 'promote'
```

Start the cluster and let it replay:

```bash
sudo systemctl start postgresql@16-main
sudo -u postgres psql -d shop -c "SELECT * FROM orders ORDER BY id;"
```

```
 id | item | created
----+------+---------
(0 rows)
```

The restore reported success and the data is not there. This is the failure the introduction warned about, and it is worth understanding rather than working around.

How it shows up depends on the exact millisecond each statement committed. In the run above the table came back without rows. On a repeat of the same steps the `CREATE TABLE` landed inside the same second as well, and the result was:

```
ERROR:  relation "orders" does not exist
```

The log explains both cases:

```bash
sudo grep -E "recovery stopping|last completed transaction" /var/log/postgresql/postgresql-16-main.log
```

```
LOG:  recovery stopping before commit of transaction 743, time 2026-08-12 18:33:24.043053+00
LOG:  last completed transaction was at log time 2026-08-12 18:33:23.992598+00
```

The target `2026-08-12 18:33:24` means `.000000`. The `INSERT` committed at `.043053`, which is later, so recovery stopped just before it and kept only the `CREATE TABLE`. A target without fractional seconds silently rounds down to the start of that second.

### Step 5.3 - Restore again with the exact target

Use the full timestamp from `SELECT now()`, including the fraction:

```bash
sudo systemctl stop postgresql@16-main
sudo -u postgres pgbackrest --stanza=main --delta \
  --type=time --target="2026-08-12 18:33:24.138220+00" \
  --target-action=promote --target-timeline=1 restore
sudo systemctl start postgresql@16-main
```

`--target-timeline=1` is new here. Every completed recovery starts a new timeline, so the first restore moved the cluster to timeline 2. The moment you are aiming at still lives on timeline 1, and this tells PostgreSQL to follow that history instead of the newest one. You need it on every restore after the first.

Check the result:

```bash
sudo -u postgres psql -d shop -c "SELECT * FROM orders ORDER BY id;"
```

```
 id |   item   |            created
----+----------+-------------------------------
  1 | keyboard | 2026-08-12 18:33:24.042266+00
  2 | monitor  | 2026-08-12 18:33:24.042266+00
  3 | cable    | 2026-08-12 18:33:24.042266+00
(3 rows)
```

The rows are back and the `DROP TABLE` is not. The log confirms where recovery stopped:

```
LOG:  recovery stopping before commit of transaction 744, time 2026-08-12 18:33:27.211012+00
LOG:  last completed transaction was at log time 2026-08-12 18:33:24.043053+00
LOG:  selected new timeline ID: 3
```

Transaction 744 is the `DROP TABLE`, and it was left out.

Run `check` afterwards to confirm archiving resumed on the new timeline, then take a fresh full backup, since the old one belongs to a history the cluster no longer follows:

```bash
sudo -u postgres pgbackrest --stanza=main check
sudo -u postgres pgbackrest --stanza=main --type=full backup
```

## Step 6 - Schedule backups

Between full backups, incremental ones only store what changed. On this cluster a 29.4 MB database produced 1 MB in the repository:

```
incr backup: 20260812-183256F_20260812-183515I
    database size: 29.4MB, database backup size: 7.8MB
    repo1: backup set size: 3.9MB, backup size: 1MB
    backup reference list: 20260812-183256F
```

Create `/etc/systemd/system/pgbackrest-full.service`:

```ini
[Unit]
Description=pgBackRest full backup
After=postgresql.service

[Service]
Type=oneshot
User=postgres
ExecStart=/usr/bin/pgbackrest --stanza=main --type=full backup
```

And `/etc/systemd/system/pgbackrest-full.timer`:

```ini
[Unit]
Description=Weekly pgBackRest full backup

[Timer]
OnCalendar=Sun *-*-* 02:00:00
Persistent=true

[Install]
WantedBy=timers.target
```

`Persistent=true` runs a missed backup after the server comes back up, which matters for a machine that is not online around the clock.

Enable the timer and test the service once by hand, rather than waiting until Sunday to find out it fails:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now pgbackrest-full.timer
sudo systemctl start pgbackrest-full.service
sudo systemctl list-timers pgbackrest-full.timer
```

```
Sun 2026-08-16 02:00:00 UTC 3 days - - pgbackrest-full.timer
```

For daily incremental backups, copy both files, change `--type=full` to `--type=incr` and set `OnCalendar=*-*-* 02:00:00`.

## Conclusion

You now have PostgreSQL archiving WAL into a pgBackRest repository, scheduled backups, and a restore procedure you have actually run: a dropped table recovered down to the transaction, verified by reading the rows.

Two things are worth doing before you rely on this. Move the repository off the database server, either to a second host over SSH or to object storage, because a local-only backup shares the fate of the disk it protects. And practise a restore on a spare server from time to time, since the exact-timestamp and timeline details in Step 5 are much cheaper to learn in a rehearsal than during an outage.

The full option list is in the [pgBackRest user guide](https://pgbackrest.org/user-guide.html), and the recovery target settings are described in the [PostgreSQL documentation](https://www.postgresql.org/docs/16/runtime-config-wal.html#RUNTIME-CONFIG-WAL-RECOVERY-TARGET).
